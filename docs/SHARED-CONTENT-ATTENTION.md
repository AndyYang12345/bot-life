# 合并转发、视频预览与注意力模式

## 实现与边界

消息链路：白名单入站 → 持久账本 → 正文/引用归一化 → 展开转发/卡片 → 图片下载或视频抽帧 → 注意力决策 → DSH 工具与回复 Outbox。

参考本机 `qqbot/dsh-qqbot` 的附件下载、引用独立展示和群聊判定设计，没有复制其业务实现。旧插件的视频路径不代表实际观看；本适配器新增受控抽帧。能力属于通道层，账本与记忆不依赖 QQ SDK。

### 合并转发

- OneBot `forward.data.id` 查 `get_forward_msg`；也支持 `data.content` 内联记录、`node.data.content/message`、已核验字段的 QQ JSON/XML 转发卡片。
- 保留消息顺序、声称的作者、正文和内嵌图片/视频。仅递归当前消息或经过同群核验的外层引用中的资源；不追踪转发内部 `reply` ID，不向模型提供任意 ID 查询工具。
- 每轮最多 3 层、30 节点、4 次转发查询、300 段、24000 字正文、8 次图片尝试、2 条外层引用。超限/过期/失败会标明，不能猜测遗漏内容。
- 展开结果写 `inbound.normalized`，媒体按 hash 与来源 role 建立关系；转发图片/视频抽帧不混入“上一张原创图片”索引。
- 转发作者只是记录中的声称，不绑定人物档案；转发原文不是发送者本人自述。记忆证据仍核验原始入站顶层文本，拒绝用展开的他人自述形成发送者个人事实。

本轮一条旧记录的资源 ID 和外层 ID 均被 NapCat 以 retcode=200 拒绝。固定版实现依赖消息映射，但不能仅据此证明本次由重启导致。没有批量回填 QQ 历史；新转发需单独群内验收。

### QQ 视频

- 原生 `video` 段及转发/引用内的视频：保存私有 hash 文件，用本机 `/usr/bin/ffprobe`、`/usr/bin/ffmpeg` 生成四张带时间点的抽样画面。
- 每轮一个，最大 128 MiB、300 秒、宽高各不超过 4096，检查 MP4/WebM/AVI 格式。单线程解码，探测/各次抽帧限时，临时目录最终删除。
- 视频流式落盘，不把完整视频缓冲进内存；下载整体限时 60 秒，失败写入有界错误分类。下载只接受 QQ CDN URL，逐次检查重定向；无可用 URL 时只向 `get_file` 传入已收到的 opaque 文件 ID，拒绝任意路径/URL。返回本地文件仅映射已有 QQ volume，realpath 拒绝越界和链接逃逸。已验证的源视频可缓存 24 小时；以外层可信会话、opaque ID 和大小分片，拒绝跨群命中，也不缓存原始签名 URL。再次引用复用源文件并重新抽帧。
- FFmpeg 不接收网络 URL、不经 shell，输入协议/容器受限；模型仍只有受限 `read_image` 和既有记忆工具，不能执行 FFmpeg 或任意下载。
- 必须实际调用 `read_image` 才描述画面。**抽样没有完整动作、音轨、ASR 或字幕**，不能声称看完整段或编造对白。
- 新环境需准备 FFmpeg/FFprobe；缺失、超限或解析失败时保留文字并说明视频未读取。增加了本地解码负担，端侧仍需实机验收。

### B 站与后续 MCP

识别纯文本、QQ JSON 小程序和链接卡片中的 B 站 URL，保留标题/简介、BV/av 标识和标准视频地址。b23 短链只识别，不跳转；不请求页面、封面、字幕或视频文件。

`inbound.normalized.links` 是结构化入口 `{platform,url,videoId?}`。后续 bilibili MCP 应经有界只读能力接入：解析标识、获取可用元数据/字幕，再按需抽帧；注明来源、时间点和覆盖范围。鉴权、预算和工具白名单单独配置，不能因为安装 MCP 就向群聊开放全部工具。

**本轮未安装或配置 bilibili MCP，也未实现通过链接自主观看完整 B 站视频。** 目前模型只能读取分享资料。

## 注意力策略

私有配置可新增以下项；缺省仍为 `replyAll`，groupModes 中使用实际数字群号，仅在现有白名单内生效：

```json
{"attention":{"mode":"replyAll","groupModes":{},"cooldownMs":20000}}
```

- `replyAll`：逐条回复兼容模式。
- `questionsOnly`：提问、@、引用 bot、图片、转发、链接回复，其余旁观。
- `attention`：明确 @bot/引用 bot 直接回应；@其他人旁观；真实图片/视频/媒体失败进入完整轮次；普通消息在冷却后交给模型判断 speak/observe。

判定使用既有 DSH provider/model 和独立密钥，对 DeepSeek 判定显式关闭推理，无工具，160 输出 token、8 秒限时、严格 JSON。输入为展开后的正文、同群最近 8 条各最多 700 字、当前人物可见记忆、角色说明。失败按超时、截断、JSON/协议等类别记录，不输出提供商原始错误，随后降级为正常回复。转发里的伪 @ 不算当前发送者在 @bot。

判定与完整回复分别占用现有持久每小时模型预算；判定用量标记 `purpose=attention`，与 chat/后台整理分开统计。决策入账，恢复时复用。冷却依据实际确认回执，重启有效。

observe 不建立回复 Outbox，但原始消息、展开正文、明确偏好观察和后台整理资格保留。之后的回复使用同群有界消息窗口，遵守 `/new` 和入站顺序，不取其他群或未来消息。

这一步只决定**收到消息后是否接话**。无入站消息时的主动对话、每日主动预算、安静时段和过期草稿仍待开发。

## 正式环境与真实样本（2026-10-21）

新版本只在测试群群启用 attention，示例群 B保留 replyAll；白名单/私聊边界不变。部署前保存私有 adapter 配置及数据库备份，QQ 未重启，适配器/记忆服务正常。

博士发送的新合并转发实际展开 6 节点、4 图片、无媒体失败，DSH 实际调用 read_image 4 次，回复获得平台确认回执；同群引用该转发也展开成功。实际视频为 96,078,288 字节、39.402 秒，最初被 32 MiB 限制拒绝；调整为 128 MiB 流式落盘后，对原样本只读重试成功下载并生成四帧（约 11.6 秒），没有追加群消息。视频修复后的群端视觉回复仍需单独确认，不能用只读抽帧成功替代。

正式环境一次判定触发过回退；原调用未显式关闭推理，固定 DSH 的 DeepSeek 适配器在未指定时可能默认 high。后续已对本 provider 的判定显式设置 off，并补齐失败分类；隔离真实 API 复核通过。历史那次失败没有具体分类证据，不能据此断言根因。

随后的一次真实引用视频在入站后 30.17 秒结束归一化，媒体失败；与当时 30 秒下载上限相符。同一引用资料的只读下载成功。已调整为 60 秒，并加入同群 opaque ID 缓存、缺失 URL 时 NapCat 的 MD5.mp4 ID 兼容，以及媒体失败分类。组内缓存不允许用于其他群；缓存命中仍由当前收到的事件授权本轮看图路径。

最终真实群端复核：博士再次引用同一视频后，videos=1、mediaFailures=0，DSH 实际 read_image 4 次，任务 done，回复 Outbox confirmed。四帧仅代表抽样视觉输入，未执行音频识别；平台确认接收与接收端人工判断描述准确性仍需区分。源码与部署均由 Git 管理，私有凭据、聊天和媒体未提交。
